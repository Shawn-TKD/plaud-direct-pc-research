# From a new Note Pro to a direct Windows connection

This is a reproducible account of an owner-controlled Note Pro onboarding on
2026-09-16. Identifiers and credential values are deliberately omitted. The
device ran V1.7.0 according to the PLAUD developer portal. Nothing here assumes
that a NotePin S firmware image is the Note Pro firmware.

## What each identity does

| Item | Obtained from | Used by | Persist for offline BLE? |
| --- | --- | --- | --- |
| Client ID + Client Secret | PLAUD developer app settings | Partner Token request | No; keep the secret out of the APK |
| Partner Token | Authentication API | User Token request | No |
| Stable User ID | Your partner application's user mapping | User Token request | Keep the same value for the same owner |
| User Access Token (JWT) | Partner API | `gen-key`, `sn-sign`, cloud bind | No; it expires |
| SN signature | `sn-sign(type, sn)` | Device pre-handshake | Yes |
| RSA public/private pair | `gen-key` | Session key exchange and audio decryption | Yes, with private-key protection |
| Bind identity | JWT `sub`, normalized for BLE | CMD 1 binding handshake | Yes |
| ChaCha20 key/nonce/AAD | Generated by device per connection | Encrypted BLE traffic | No |

The SN signature is **not the JWT**. The NotePin S V1.2.7 firmware's public key
verified the Note Pro signature over the raw serial number, and no timestamp or
client RSA public key was part of that signed message. This is local evidence
for the current devices, not a promise that PLAUD will keep the same trust root
or policy in future firmware.

## Observed sequence

1. Create or select a PLAUD developer app. Record its Client ID and generate a
   Client Secret. Choose a stable application User ID; changing it changes the
   user-level identity. Do not copy credentials into source control.
2. Exchange Client ID + Client Secret for a Partner Token, then mint a User
   Access Token for that User ID. In this case `expires_in` was 86,400 seconds.
3. The Android bootstrap app received the User JWT at runtime and initialized
   the official PLAUD SDK against `platform-us.plaud.ai`. The SDK successfully
   called `gen-key` **before** any successful BLE scan.
4. The first BLE scan failed because the phone had not yet granted Bluetooth
   scan permission. After permission approval and a new scan, the exact Note
   Pro appeared. This failure was a phone permission issue, not authentication.
5. The app called `sn-sign(type=notepro, sn=...)`, then used the official SDK's
   BLE pre-handshake and RSA session setup. Device bind status was 0. The cloud
   `sdk/bind` request returned HTTP 200 and `is_bind=true`; the portal then
   listed the Note Pro. The device returned an empty recording list.
6. Android stored the signature, RSA pair, and bind identity in an
   Android-Keystore-encrypted blob. Its exporter wrapped that blob to a
   PC-generated RSA public key, with AES-256-GCM for the payload.
7. The PC imported the encrypted envelope and sealed its contents with Windows
   DPAPI. The phone bootstrap app was stopped. Windows then connected directly
   to Note Pro twice in separate BLE sessions and read battery, storage, and
   the empty file list. Neither PC connection supplied a JWT or contacted the
   PLAUD API.

The portal screenshot showing the device is evidence of the successful cloud
bind, not evidence that the Note Pro contacts the cloud during every BLE
connection. The Bluetooth device accepts local cryptographic proof.

## Why the phone was used, and how to shorten the route

The phone is not a cryptographic requirement of the Note Pro. Officially,
PLAUD ships Android and iOS Embedded SDKs; the Android SDK provides the
`gen-key`, `sn-sign`, BLE, and export plumbing used here. A Windows Python
implementation of the same documented partner API flow exists in this project,
but this machine's direct API request received HTTP 403 / Cloudflare code 1010.
The user-visible Partner and User Token requests succeeded in the PLAUD
Playground, so the blocker was the API client path to SDK endpoints, not the
existence of a valid user JWT. We did not circumvent that edge response.

For a **second computer using an already provisioned device**, use the existing
encrypted recipient-key migration. No phone, new JWT, or `sn-sign` call is
needed. Use the same owner identity and connect one host at a time.

For a **new device**, the most useful optimization is to separate credential
preparation from BLE pairing. `gen-key` and `sn-sign` take the JWT and known SN;
they do not require the phone to be connected to the device. The companion app
now offers an experimental “prepare PC credentials” choice. It obtains and
encrypts the materials on Android, exports to the PC recipient key, and leaves
the first BLE handshake to Windows. The conventional Android-first path remains
available and was the path validated in this case. The prepare-only path still
needs a fresh-device field test; a portal cloud bind may also be needed if
portal registration matters.

If PLAUD supplies an officially supported desktop API route, `provision-notepro`
can remove Android altogether: Partner Token -> User JWT -> `gen-key` ->
`sn-sign` -> DPAPI -> Windows BLE. The direct call must be permitted by PLAUD;
HTTP 403 / code 1010 should be treated as a support question, not as a cue
to change fingerprints or use an indirect bypass.

When a User JWT already exists, the CLI accepts `--user-token-stdin --sn ...`
without a Client Secret config, reducing the number of credentials handled on
the desktop. This does not change the API access restriction observed here.

## Repeating the validated Android-first path

1. Build the Android bootstrap variant with `-PnoteProBootstrap=true`. An
   optional `-PbootstrapSn=881...` limits its scanner to one device. Without
   that option, it shows Note Pro serial numbers only. The user token is
   entered at runtime and is not embedded in the APK.
2. On the PC, run `plaud-pc bootstrap-init --state-dir .local-state-notepro`.
   Install the debug app and copy the resulting public PEM into its private
   `files/pc-bootstrap-public.pem` using an authorized ADB `run-as` session.
3. On the phone, grant Bluetooth scan/connect permissions. Enter a current User
   Access Token, choose “phone connection verification,” select the target SN,
   and wait for bind status 0. Do not clear an existing device's binding as a
   routine step; a different owner can produce a token mismatch.
4. Restart the app if the public PEM was copied after initial launch. Retrieve
   `files/pc-bootstrap-v1.json` over `adb exec-out run-as`. Only this encrypted
   envelope should cross to the PC.
5. Run `plaud-pc bootstrap-import`, stop the phone app, then run
   `plaud-pc connect-readonly`. Repeat once after the first BLE session closes
   if you want to establish that local reconnection works.

The complete commands live in the project README. Device recordings are not
deleted by any of these bootstrap or read-only steps.

## Limits of the evidence

- Two immediate Windows reconnections establish repeatability across sessions,
  not indefinite durability across firmware upgrades, reset, re-binding, or
  changes to PLAUD's signing policy.
- A Note Pro V1.7.0 OTA image was subsequently downloaded and compared with
  NotePin S V1.2.7. It contains the same PLAUD SN-verification public key and
  explicit signature-verification and ChaCha session code, while its hardware
  layout differs. This strengthens the cross-model evidence but does not
  validate first-time PC-only provisioning or Wi-Fi transfer. See the
  [firmware comparison](../../firmware-research/NOTE-PRO-VS-NOTEPIN-S.md).
- A cached device signature and RSA private key are sensitive owner credentials
  even though the JWT has expired. Protect migration files accordingly.
